---
title: batch_runs
description: Configure how large each run should be.
---

In a large repository, it may not be possible to run all workspaces in a single GitHub Action run due to CPU and disk space limitations.  The `batch_runs` configuration allows specifying the maximum number of workspaces in individual action runs.

## Default Configuration
```yaml
batch_runs:
  enabled: false
  max_workspaces_per_batch: 1
  merge_steps: setup
```

## Keys
| Key | Type | Description |
|-----|------|-------------|
| enabled | Boolean | Specifies whether the batch runs is enabled. Default is false. |
| max_workspaces_per_batch | Integer | Maximum number of workspaces that each run can contain. Default is 1. |
| merge_steps | String | Which steps can join an action run that is already running. One of `none`, `setup`, `setup_and_plan`, `all` or `by_phase`. Default is `setup`. |

## Functionality
If batch runs is enabled, the following happens:

1. If the number of workspaces that can be run in a single action run is greater than `max_workspaces_per_batch`, additional action runs will be created with the additional workspaces.

## Merging steps

Terrateam puts the steps of a job into as few action runs as it can.  Many runs are slower than one run.  The `merge_steps` key gives which steps can join an action run that is already running.  A step that the value does not permit always starts an action run of its own.

Four of the values make a ladder of the highest step that can join.

| Value | The steps that can join a run |
|-------|-------------------------------|
| `none` | None.  Each step gets an action run of its own. |
| `setup` | The tree builder, the config builder and the indexer. |
| `setup_and_plan` | The steps above, and a plan. |
| `all` | The steps above, and an apply.  A run of many layers then uses one action run. |

The fifth value, `by_phase`, is not on that ladder.  See [Phases](#phases) below.

A step joins a run only if the run can take it.  The run must have the same environment, the same `runs_on` and the same refs, and the cap `max_workspaces_per_batch` holds for the full run.  A step that cannot join gets an action run of its own.

The `enabled` key does not control `merge_steps`.  The `enabled` key controls `max_workspaces_per_batch` only.

Terrateam reads `merge_steps` from the configuration file in the repository.  A configuration that the config builder makes cannot set it, because the tree builder, the config builder and the indexer run before that configuration exists.

`merge_steps` changes how many action runs hold the work of a job.  It changes nothing else.  It cannot make an operation that the rest of the configuration does not permit, and it cannot stop an operation that the rest of the configuration permits.  A plan and an apply that happen automatically today happen in the same order with any value of this key.

## Phases

The steps of a job fall into two phases.

| Phase | The steps of the phase |
|-------|------------------------|
| Setup | The tree builder, the config builder and the indexer. |
| Layer | A plan and an apply. |

`merge_steps` of `by_phase` permits every step, as `all` does, but only into an action run of the same phase.  An action run thus holds one phase and never both.

```yaml
batch_runs:
  merge_steps: by_phase
```

Take `by_phase` when the work that prepares a job must keep an action run of its own, and the layers of that job must still share one run.

### Example

A pull request has the three steps that prepare a job and three layers.  The first two layers have no changes, so Terrateam plans the next layer without a comment from a user.  The third layer has a change and stops the job at the plan comment.

| Value | The action runs |
|-------|-----------------|
| `none` | Six.  One for each step. |
| `setup` | Four.  One for the three setup steps, and one for each layer. |
| `setup_and_plan` | One.  A plan joins the run of the setup steps. |
| `all` | One.  The same as above, and an apply would join as well. |
| `by_phase` | Two.  One for the three setup steps, and one for the three layers. |

The tree builder of a pull request builds the tree of the destination branch as well.  That build always takes an action run of its own, whatever the value of `merge_steps`, because a step joins a run only when the refs agree and this one has the ref of the destination branch.  The counts above are the runs of the pull request, and they do not hold that one.

## Considerations

Terrateam does not limit how many action runs it will run at concurrently.  For example, if a change has 100 workspaces, and `max_workspaces_per_batch` is set to `1`, Terrateam will create 100 GitHub Action runs at the same time.
